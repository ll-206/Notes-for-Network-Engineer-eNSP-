IP

只要是能上网的设备，必须具有一个IP地址。

数量2³²

IP地址的结构

总长度：32 bit(IPV4)

表示：x x x x x x x x . x x x x x x x x . x x x x x x x x . x x x x x x x x（二进制）

或者十进制也可（每八个bit一个字节）

组成：网络位+主机位

网络位：同一网段中，所有设备的网络位相同

主机位：同一网段中的具体设备，同一网段中必须唯一。

IP地址的掩码

作用

区分IP地址中的网络位和主机位

特点

掩码的长度与IP地址的长度，完全相同，一一对应；

左边是1右边是0,1和0永远不会交叉出现。

在同一网段中的设备网络位相同（同一个IP地址，掩码不同，所属的网段就不同）

原理

在掩码中，与IP地址的网络位对应，用1表示，保留；

与主机位对应时，用0表示，变为0。

格式

点分十进制：例，255.255.255.0

纯二进制：例，11111111 11111111 11111111 00000000

书写：/24（共有二十四位是1）

例：192.168.10.25/24
/24 表示：前 24 位是网络号，后 8 位是主机号
对应掩码：11111111.11111111.11111111.00000000

即 255.255.255.0

所以：
网络号：192.168.10.0
主机号范围：192.168.10.1 ~ 192.168.10.254

（.0 是网络地址，.255 是广播地址，不能给主机用）

特殊IP地址

每个网段中都有2个特殊的IP地址网络地址

网络地址

主机位全为0的IP地址，称之为网络地址。表示的是某个IP网段的地址的“范围”。

广播地址

在主机位全为1的IP地址，称为广播地址。表示某个IP网段里的所有的主机/设备。

-【默认掩码是 255.255.0.0 | /16】

D类

最左边的4个bit，固定不变，是1110 ，这种类型的地址叫做D类IP地址；

-【该类型的IP地址属于组播地址，没有掩码而言】

多用于视频会议、直播。

最左边的4个bit，固定不变，是1111 ，这种类型的地址叫做E类IP地址；

子网划分

未划分的情况：

两个公网设备之间，此时仅仅只有1个互联链路。理论上是需要两个在这个网段的IP地址即可。

以分配方案——>200.1.1.0

属于C类地址，并且使用默认掩码，255.255.255.0，该网段中，理论上的主机IP地址的个数，应该是：2的8次方，也就是 256个。

200.1.1.0 -- 200.1.1.255 抛去两个特殊的IP地址不能使用，可用为254个

但实际上，这两个设备只使用两个公网地址，也就是说浪费了252个公网地址。

属于同一个IP网段中的主机地址，如果没有被该网段的主机使用，那么也不能使用在其他的网段的主机上。

<子网划分>案例练习：

而子网划分实质为：网络位增大，主机位减少，需要2^n个地址就留下多少n个主机位。

数据通信流程

MAC地址

前言

IP地址具有唯一性，但是可以随意更改（私有地址可以在不同的局域网重复使用）

而MAC地址全球唯一（物理地址、硬件地址）

理解：

收件人名字——IP地址

收件人地址——MAC地址

任何两个网络设备之间通信的时候，必须得同时知道对方的IP地址和MAC地址。

MAC地址概述

即任何一个联网的看得见的摸得着的“硬件设备”，一定是有一个MAC地址的。

长度是48 bit，即:6个字节。

例子：98-60-08-2D-E9-59

结构：

  • 前半部分，称之为厂商代码；【可以通过网站查询，确定网卡所属的厂商】
    *后半部分，称之为设备编号；

分类：

  • 单播MAC地址，该类型的MAC，仅仅表示一个设备；
    该类型的MAC地址，第8 bit为0（第一个字节的最后一个bit）
    *组播MAC地址，该类型的MAC，可以表示多个设备；
    该类型的MAC地址，第8 bit为1（第一个字节的最后一个bit）
    *广播MAC地址，该类型的MAC，可以表示所有设备；
    该类型的MAC地址，所有bit，全都是1。换成16进制以后的样子就是：
    FF-FF-FF-FF-FF-FF ，也叫 全F 的MAC地址，也叫广播MAC地址。

网络中的数据转发的方式，分为三种类型：
*单播转发，该类型的转发方式的数据包：目标IP和目标MAC地址，都是单播IP和单播MAC


*组播转发，该类型的转发方式的数据包：目标IP和目标MAC地址，都是组播IP和组播MAC


*广播转发，该类型的转发方式的数据包：目标IP和目标MAC地址，都是广播IP和广播MAC

流程概述

正常通信：是双向的，产生——传输——接受

流程：

产生/发送报文

传输报文

接受报文

流程概述之发送报文(OSI模型)

通信流程之产生报文：
*通常情况下，我们在设备之间发送信息的时候，肯定是通过某些工具/软件来实现的。
*同时，这些信息和数据，最终一定是通过设备上的“网口/网卡”连接着的网线传输出去的。
*所以，这个数据从软件产生，到从网卡发出去，这个过程，都是在一个设备的内部发生的。
*这个过程，就叫做“产生报文”。

首先要了解 OSI 模型(open system inter-connect reference model)

世界上的任何一个联网的硬件和软件，他们的开发标准，都在 OSI 模型中，统一固定好了。

所以，大家都是依靠同一个模型制造出来的，所以彼此之间的通信，才不会出现问题。

但是， 这个OSI模型，仅仅是一个参考模型。
同时，在实际的生产环境中个，我们使用的，其实是 TCP/IP 模型。无论是OSI模型，还是TCP/IP模型，每一层都能实现很多很多的功能。
实现这些功能时候，依靠的都是各种类型的“协议”。
所以，我们在研究 TCP/IP 模型的某一层功能的时候，其实本质上是需要研究这一层的“协议”。

在OSI中

应用层：

7、应用层

对应程序提供接口（相关设备、软件、所有终端用户应用程序）

6、表示层

数据格式的转换，变成机器语言，或者加密格式，确保兼容（编码、加密、压缩）

5、会话层

在通信双方之间建立，管理和终止会话

（以上在TCP中看做用于程序开发统称为应用层）

4、传输层

决定传输的效率和质量

3、网络层

编址，逻辑寻址（IP、路由）

2、数据链路层

将数据封装成帧，建立逻辑连接（MAC、帧）

1、物理层

在媒介上传输比特流，提供机械和电气的规约

我们的数据产生以后，最终需要通过物理层的网线转发出去。
那么，从应用层产生到物理层的这个过程，中间会经过很多很多层。
每经过1层的时候，都会添加一个“协议”的头部信息，在这个头部信息中，就体现出来了
该层将要实现的某些功能。

那么这个不断的添加协议头部的过程，被称之为：数据封装。类似于“快递打包“

每经过一层都会添加一个协议头部信息，告知后续传输网络及接受设备该数据如何处理

数据单元名称：

应用层—>数据流 传输层—>段 网络层—>包 数据链路层—>帧 物理层—>位

流程概述之传输报文(OSI模型)

让组成中间的这个“传输网络”的网络设备（交换机，路由器等），基于报文的特定头部信息，不断地进行转发。

流程概述之接收报文(OSI模型)

就好比说接收快递的过程。
当我们说到快递以后，肯定是从外向内，一层一层的拆包装。
所以，首先查看的就是第二层的头部信息，在里面我们需要确认一下目标MAC是不是自己家；
同时，还得检查一下这个快递的外包装是否存在损坏的问题，也就是“数据校验”；

所以，其次查看的就是第三层的头部信息，在里面我们需要确认一下目标IP是不是自己的名字；
那么这个不断的拆解协议不投的过程，被称之为：数据解封装。类似于“拆包包裹”！

服务类别（type of service）：出现数据过多，端口不够时，需要处理的的优先权，通过值表示，值越大，优先级越高。

TTL： 存活时间，数字表示，防环，数据包每经过一个路由器减1，为0时数据包被丢弃。

protocol：协议字段，表示IP头部后面头部包含的是什么协议的数据包。

source ip address和destination IP address：源IP和目标IP地址

四层：

不同应用程序使用的端口号不同，知道端口号能精准地传输数据

source port：源端口，用于表示源接口上“发送设备”的某个应用程序

destination port：目标端口，用于表示“目标设备”上的某个应用程序

sequence number：序列号，为每个数据包编号，实现可靠传输。

aknowledgement number：确认号，用于传输每个数据包（期望收到的下一个字节的序号）

没有序号和确认号，传输迅速，但可靠度比tcp低，适应于视频通话、会议、语音通话等。

路由器分析第三层（网络层，IP）

网卡上有mac地址、IP地址而且还是可见设备（一、二、三层）单选则为第三层

ARP协议（第三层）

背景概述

数据想要转发需要IP头部的封装

而 IP 头部有源IP和目标IP，目标IP难以记忆。

解决方法：网址转化为IP

类似电话薄，IP为电话号码，备注为域名

通过DNS技术将网址解析成IP地址

解决了IP头部，数据链路层还需要解决mac地址的问题：源mac已知可目标mac地址未知

把人类容易记忆的域名，转换成计算机通信所需的 IP 地址。

  • DNS 帮你查到：93.184.216.34

arp概述

ARP协议被称之为address resolution protocol，地址协议协议。
主要作用就是：基于已知的目标IP地址，获得其对应的目标MAC地址。

🔴ARP 表

IP—>Mac映射表（缓存）

动态条目： 这是最主要的形式，通过 ARP协议自动学习 得来。 由系统自动添加、更新和删除。管理员无法干预其学习过程。

静态条目：由网络管理员手动配置。不会自动过期，始终存在于缓存中，除非手动删除或设备重启。

这个也被称之为“ARP表”，这里面的条目，也被称之为 ARP 条目。

🚩协议工作原理：

  • 首先发送数据包要知道Mac地址，先查看本地的“缓存表”
  • 如果没有找到对应的条目，源设备就会发送一个 arp 协议的“请求报文”，以广播的形式发送。（只能发送给与发送设备在同一个网段的所有终端设备）该网段中收到“请求报文”的设备开始进行解封装了。
  • 接收的设备先分析了二层头部，即目标Mac地址，检查是否和自己的Mac符合。（因为是广播Mac地址，代表这个网段的所有设备，可以继续解封装）接着查看类别字段，type—>ARP
  • 查看到ARP类型后，第二层头部的解封装完成（查看MAC地址，是否是本设备能接收的），由于第一次发出的是广播，该网段下所有主机都可以接受，并且当分析出二层中下一层的类型为：0x0806，即ARP协议类型，接下来的第三层给ARP协议处理。
  • 接收的设备检查各字段，保存报文的源IP和源MAC地址，并记在本地缓存表。确认报文中包含的“目标IP”是否和自己的相同。
  • 若相同，则返回一个ARP响应报文（已知发送报文的设备的IP和MAC，所以可以直接发送，不用查）；若不相同，则丢弃报文。单播
  • 该响应报文顺利的传输到 PC1 以后，PC1也开始进行解封装：
    首先，接收主机(PC1)开始分析2层头部的 “目标MAC地址”，看看自己是否有资格接收该报文。
    对于ARP响应报文而言，目标MAC地址是“单播MAC地址”，此时表示的是PC1的MAC。
    所以可以正常的接收该报文。
  • 随后，开始分析2层头部中的“类型”字段，发现该字段的取值是：0x0806，表示的是ARP协议。
    所以，PC1就直接将2层头部干掉，然后直接扔给第3层的ARP协议，进行处理。

交换网络的问题

不足

无法隔离广播域

影响

通常情况下，同一个网段的多个主机，是通过交换机进行互联的；
-交换机在收到“广播数据”的时候，只能是无脑的进行“广播/洪泛/泛洪/Flooding .
*如果交换机收到的“广播数据”是一个合法的数据，此时确实是应该广播处理。
*如果交换机收到的“广播数据”是一个恶意的病毒，如果依然按照广播处理，那么就会影响到同网段的所有主机。

为什么无法隔离广播域？

（1）当交换机收到一个广播数据的时候，交换机按照工作原理的流程去分析该数据：
*先分析源MAC地址，形成MAC地址表
*再分析目标MAC，查找MAC地址表。

（2）因为我们当前收到的是“广播数据”，所以这个“广播数据”的2层头部的“目标MAC”是 广播MAC，即 全 F 。 所以此时交换机会查找全F的MAC地址表条目

（3）如果能找到对应的MAC地址条目，则从该条目中指定的端口发送出去；
如果找不到对应的MAC地址条目，则直接广播。

（4）👉在交换机的MAC地址表里肯定找不到全F的条目，因为交换机的 MAC 地址表是通过学习源 MAC 建立的

👋🏼解决办法——VLAN技术

virtual local area network，即：虚拟局域网

基于网络的规模进行分类

网络类型有→LAN,局域网（指范围较小的网络，通常指家庭网络或者是企业网络）

→MAN，城域网（指一个城市级别的网络）

→WAN，广域网（全世界范围内的网络 |企业网络）

😋概述

VLAN称之为虚拟局域网，指的是属于同一个 VLAN 的网络设备/终端设备，他们的物理位置可以不在一起。对于属于同一个LAN或者同一个 VLAN 的设备而言，他们之间的通信，依靠的都是“私有IP地址”。

作用

在交换机上，实现广播域的隔离。不同的 VLAN 之间的端口，是无法实现互通的

tips：交换机上任何一个端口都会属于某一个VLAN

交换机上划分看vlan之后，本质上是将交换机的MAC地址表按照vlan进行了分割（每个vlan都对应这一个独立的小的MAC地址表）

普通局域网

  • 一个交换机 = 一个广播域
  • ARP / DHCP 会广播给所有设备

VLAN

  • 一个交换机 = 多个广播域
  • 广播被限制在 VLAN 内

😋vlanID

VLAN 是通过一个“ID”来表示，ID，取值空间为0到4095，一共4096个。（能用的是1到4094）

且默认情况下，所有端口都是属于vlan1的。

🔴端口类型

access端口(访问端口) ，通常用来连接“非交换机设备”
*trunk端口(干道端口) , 通常用来连接“交换机”设备
*hybrid端口(混杂端口) ，交换机的端口的默认角色。

所以这个时候就需要tag（标签）

🔴TAG(802.1Q)

位置：二层头部（数据链路层）

普通以太网帧结构：

| 目的MAC | 源MAC |Type |Data | FCS |

带 802.1Q Tag 的帧结构：

| 目的MAC | 源MAC |802.1Q Tag |Type |Data | FCS |
1、为什么需要 VLAN Tag
  • 在单台交换机上，可以通过 端口 来区分 VLAN
  • 当多个 VLAN 的流量需要通过 同一条交换机间链路 传输时，仅靠端口已经无法区分
  • 因此，需要一种机制把 VLAN 信息写入数据帧

👉 这就是 VLAN Tag 出现的原因

2、802.1Q
  • IEEE 802.1Q 是 VLAN 的国际标准，或者叫dot1q
  • 用于规定：
    • 如何在以太网帧中标识 VLAN
    • 如何在交换机之间传递 VLAN 信息

802.1Q 是给以太网帧打 VLAN 标签的标准

长度：4字节（32位）

其中12个bit作为标识vlan号所以2的12次方为4096

🤗access和trunk的对比

🤑access

主要用于连接“非交换机的设备”。

  • 特点：

    同一个链路只能传输一个VLAN的数据

  • 发送：

    发送出去的数据通常都不携带VLAN标签（如，从交换机发送给PC）

  • 接收：

    由于这种端口连接的都是非交换机吗，不支持VLAN技术

    通常收到的数据都是没有VLAN标签的

    故交换机会将端口的所属VLAN号作为无标签数据的VLAN号

收数据：添加标签

发数据：删除标签

🤒trunk

主要用于连接“交换机设备”

  • 特点

    同一个链路可以传输多个VLAN数据

  • 发送

    发送出去的数据通常是携带VLAN标签的

  • 接收

    由于通常来说，trunk链路是用于连接交换机链路的，一般收到的数据都带有VLAN标签

    是否允许接收该数据，应该由配置命令决定port trunk allow-pass vlan

tips：在交换机内部的数据，永远是有VLAN标签的。在交换机的内部就是依靠这些数据携带的VLAN标签进行隔离。

收数据：分两种情况

1、数据本身自带标签，保持原有的VLAN标签

2、数据本身没有标签，使用trunk端口的pvid参数作为该数据的vlan标签

发数据：两种情况

1、保持原有的标签

2、如果携带的标签等于trunk端口的pvid参数，那么这个数据的标签应该删去（trunk端口pvid为10，但allowpass也有vlan10，这个时候发送一个携带vlan10的数据，它的标签依旧会被删去）

如何修改trunk链路的pvid？

命令：port trunk pvid vlan xxxx

access链路就直接用那个default那条命令即可

🫥vlan链路类型之hybrid

概述

混杂端口——既可以实现access端口也可以实现trunk功能，或者同时实现两者的端口的功能。

🔴特点：

接收数据时：

  • 如果接受到的数据没有任何标签，就将该进入端口的PVID作为该数据的vlan标签。
  • 如果接收到的数据带有标签，则看标签是否和端口允许该vlan

发送数据时：

  • 首先看数据携带的vlan号是否被允许；
  • 如果允许，则观察untagged和tagged的操作
    若是untagged，则直接干掉vlan标记，然后发送出去；

    若是tagged，则带着vlan标记发送出去；

    若没有对该vlan号配置命令的话，则查看这个vlan号和pvid是否一样，若果一样，则发送出去且删去vlan标记。

    （如果标记了tagged并且vlan号和pvid一样，也要带着vlan号出去）

将网关接口配置在三层交换机上

VLAN 与 Vlanif 的关系

  • VLAN：

    二层逻辑广播域，用于划分和隔离二层网络，不具备三层通信能力。

  • Vlanif：

    建立在 VLAN 之上的三层逻辑接口，用于为设备提供 IP 能力。

  • 关系：

    Vlanif 依附于 VLAN 存在，一一对应（VLAN X ↔ Vlanif X），

    VLAN 负责二层划分，Vlanif 负责三层通信。

  • 结论：

    VLAN 本身不能配置 IP，IP 配置在 Vlanif 接口上；

    是否能实现 VLAN 间路由，取决于设备是否支持三层转发能力。

 port default vlan 20

路由条目本质上就是一个网段

路由条目的类型：


📌直连路由：表示的是设备自己的接口上配置的IP地址所属于的网段。 即direct

  • 来源：接口配置 IP 后自动生成
  • 特点：
    • 优先级最高（Pre = 0）
    • 不需要配置
    • 一定存在
  • 作用：
    • 表示该网段就在本设备上

📌静态路由：表示的是为了与某个特定的网段互通，人为手动添加的路由条目。 static

  • 来源：管理员手工配置
  • 特点：
    • 稳定
    • 不自动变化
  • 适用场景：
    • 小型网络
    • 缺省路由
    • 指定路径转发
ip route-static 0.0.0.0 0 10.1.1.1

📌动态路由：为了与特定的网段接通，路由器之间按照某种规则学习的路由

  • 来源：路由协议学习
  • 常见协议：
    • RIP
    • OSPF
    • IS-IS
    • BGP
  • 特点：
    • 自动学习
    • 可动态收敛
  • 适合：
    • 中大型网络

Interface 决定数据包从路由器的哪个接口发出；

NextHop 决定数据包在三层上交付给哪个下一跳 IP

NextHop是数据从路由器出来后的三层交付IP

🤷🏼‍♀️静态路由

首先，我们知道路由表的工作原理：

当路由器收到一个数据包，查看的是IP头部的目标IP地址，

将目标IP地址与“路由表条目”进行比对/匹配：

  • 如果匹配成功，则直接从“条目”对应的端口中发送出去；
  • 如果匹配失败，则直接丢弃。

😬路由表条目的主要结构

目的网段/掩码|出接口|下一跳

路由条目能放入路由表的前提：

下一跳的IP地址必须互通（可到达）

👇🏼数据与条目匹配过程

  • 数据进入路由器后，路由器只关注数据的目标IP地址
  • 而路由表则只关心被掩码覆盖的目标IP的bit（网络位/网段）
  • 用路由条目的掩码覆盖目标 IP，比较得到的网络位是否与该条目的目的网络一致，若多条一致，则选择掩码最长（前缀最长）的路由作为最终匹配结果。
  • 如果没有成功匹配的结果，则丢弃数据。

❣️那在ping的过程中源IP怎么判断自己的IP地址和目标IP地址是不是同一个网段呢？

用自己IP地址的掩码来覆盖目标掩码，看看网络位是否相同（因为不知道目标IP的掩码）

例子：

👀首先，数据的目标IP：10.1.1.1

路由表条目：
编号	目的网络	掩码	出接口	  下一跳
路由①	10.1.1.0	/24	  GE0/0/0	  1.1.1.2
路由②	10.1.0.0	/16	  GE0/0/0	  1.1.1.3
路由③	10.1.1.0	/25	  GE0/0/0	  1.1.1.3

👏🏼接着用各个条目的掩码覆盖目标IP

对于路由1：掩码为24位，即 10.1.1.1 →10.1.1.0 和条目匹配。

对于路由2：掩码为16位，即 10.1.1.1 →10.1.0.0 和条目匹配。

对于路由3：掩码为25位，即 10.1.1.0000 0001 →10.1.1.0 和条目匹配。

🧠最后在多个匹配成功的条目中找到掩码覆盖的网络位（前缀 bit 数）最长的，进行转发。

🧏🏼生成树协议STP

🐷产生的背景

在交换网络中存在单点故障的问题

🌐在上面这个拓扑中，如果交换机SW1和交换机SW2之间的链路坏了或者不存在了，就会导致PC1和其它两个主机不能互通，这就是单点故障。

系统中没有冗余、不可替代的组件，一旦该组件失效，会导致整个系统或核心业务不可用。

🍊解决办法：

线路/设备备份

但是留下了另一个问题：二层环路。

🤔二层环路的产生

二层交换机转发有两个关键特性：

  1. 二层以太网帧没有 TTL（生存时间）

    路由器的 IP 包有 TTL，会“跳数减 1”，减到 0 就丢。

    但二层帧没有这个机制，所以不会自动停止。

  1. 交换机对广播/未知单播会“泛洪”
    • 广播：FF-FF-FF-FF-FF-FF（比如 ARP 请求）
    • 未知单播：交换机不知道目的 MAC 在哪（MAC 表里没有）

      这两种都会从除入端口外的所有端口发出去。

—所以同一个广播回绕回来并且会产生广播风暴、MAC地址震荡、CPU占用升高。

🤷🏼‍♀️MAC地址震荡：

在存在二层环路时，同一台 PC 发出的帧，

会在“同一台交换机”上被认为是从“不同接口”进入的，

从而导致该 PC 的 MAC 地址在 MAC 表中不停地在不同端口之间切换（PC不变，但是入接口一直更新，MAC地址表条目一直在更新变化）。

💦背景总结：

以太网交换网络中为了进行链路备份，提高网络可靠性，通常会使用冗余链路。但是使用冗余链路会在交换网络上产生环路，引发广播风暴以及MAC地址表不稳定等故障现象，从而导致用户通信质量较差，甚至通信中断。为解决交换网络中的环路问题，提出了生成树协议STP（Spanning Tree Protocol）。

👀概述

STP是一个用于局域网中消除环路的协议。
—运行该协议的设备通过彼此交互信息而发现网络中的环路，并对某些接口进行阻塞以消除环路。
—STP在网络中运行后会持续监控网络的状态，当网络出现拓扑变更时，STP能够感知并且进行自动响应，从而使得网络状态适应新的拓扑结构，保证网络可靠性。

🪪CIST

CIST = Common and Internal Spanning Tree

公共与内部生成树

MSTP 里可以有很多“分支树”（MSTI），但必须有一棵“总干树”，这棵总干树就叫 CIST。

🪪CIST Bridge (本桥 ID)

🪪CIST Root/ERPC(根桥 ID)

CIST Root/ERPC :32768.4c1f-cc63-6211 / 20000

生成树协议中，被全网共同选出来的“参考原点”。所有交换机都会以它为中心来计算路径、决定端口是转发还是阻塞。

🪪根桥的选举

STP 启动后，所有交换机互相发送配置 BPDU，比较桥 ID，桥 ID 最小的那台当选根桥。

找到根网桥之后，其它交换机就是非根交换机

桥ID的比较：

首先先比优先级，优先级最小的即可作为root

如果优先级相同再比较MAC地址,选出MAC地址最小的作为root。

详细流程是：

每一台交换机，都会从所有 STP 端口发 BPDU，使用 配置 BPDU（Configuration BPDU），所有开启 STP 的端口都会周期性发送 BPDU

1️⃣ 初始状态

  • 每台交换机都认为自己是根桥
  • 发送 BPDU，BPDU 中：
    • Root ID = 自己的 Bridge ID

2️⃣ BPDU 交换

  • 交换机从各端口接收其他交换机的 BPDU
  • 将 收到的 Root ID 与 自己的 Root ID 比较

BPDU 里面装了什么？

你可以把 BPDU 想象成一张包含以下信息的名片：

  • 根 ID (Root ID)：发送者认为的根桥是谁。
  • 桥 ID (Bridge ID)：发送设备的桥ID。
  • 路径开销 (Root Path Cost)：有多远。
  • 计时器参数：多久发一次，默认 2 秒。
BPDU的类型：1.配置 BPDU (Configuration BPDU) 2.TCN BPDU (Topology Change Notification) 第一种Configuration BPDU主要用于选举根桥和维护生成树拓扑 第二种Topology Change Notification主要用于告警情报，当某台交换机发现自己有个接口断了或者新插了线，拓扑变了，它会发这种报文告诉老大（根桥），让全网更新 MAC 地址表

🪪Root Port（根端口）

特点：

  • 唯一性：每一台非根桥交换机有且只有一个根端口。
  • 职能：它是该交换机通往根桥的“最优路径”。
  • 状态：根端口始终处于 Forwarding（转发） 状态，负责收发流量。

根端口的选出：

  • 最小的根路径开销（RPC）：
    • 也就是从这个接口走到根桥，路上的“路费”（带宽代价）总和最少的胜出。
  • 最小的对端桥 ID（Sender BID）：
    • 如果路费一样，就看对面接的交换机谁更牛（ID 更小）。
  • 最小的对端端口优先级（Sender PID）：
    • 如果对面是同一台交换机，就看对面那个口的优先级。
  • 最小的对端端口索引（Sender Port ID）：
    • 如果前面都一样，最后看对面物理接口的编号（比如对面接的是 G0/0/1 还是 G0/0/2）

如何知道是不是根端口？

  • 每条路径的开销计算，在表[Port1(GigabitEthernet0/0/1)][FORWARDING]查看字段Port Cost，例子： Port Cost(Dot1T ) :Config=auto / Active=20000 此时这条路的开销为20000
  • 或者查看CIST Global Info里的CIST RootPortId :128.3 字段，这里128是默认的端口优先级，3就是根端口。（端口优先级可以修改，步长为16）
  • 也可以在表Port1(GigabitEthernet0/0/1)][FORWARDING]查看字段Port Role，如果是根端口的话，它会显示 Port Role :Root Port

🪪指定端口

第三步：确定指定端口（Designated Port）

在每一条二层链路上，STP 会选举一个用于转发数据的端口，该端口称为指定端口。

指定端口的选举规则（按优先级顺序）：
1）比较端口到达根桥的路径开销，开销小的端口为指定端口；
2）若路径开销相同，则比较端口所在交换机的桥 ID，桥 ID 小的端口为指定端口；
3）若仍相同，则比较端口 ID，端口 ID 小的端口为指定端口，另一端口为备用端口（AlternatePort）。

😑总结

  • STP的核心作用：防环
  • 防环的本质：在多个互通发链路中，找一条最好的，作为优先使用，其它都堵塞。
  • 其实实际上就是交换网络的选路技术。
  • PS只有交换机觉得自己是根交换机的时候才发BPDU

💥STP工作原理

分为

（1）生成一棵树：

  • 确定交换机角色
  • 确定端口角色
  • 确定端口状态

（2）维护一棵树

  • 一旦生成树建立之后，根交换机会周期性的发送 BPDU 报文。用来维护这棵树！
  • 默认情况下，根交换机发送 BPDU 报文的周期时间是：2s (hello)

（3）修复一棵树

  • 如果正常的STP协议端口(根端口/非指定端口)在规定的时间内，一直无法收到根交换机发过来的    BPDU，那么就会认定“当前的交换网络”出现了'故障“。
  • 接收BPDU的最大的有效时间是：20s (max-age)  *如果当前的交换机，真的发现了故障，那么就 会开始进行”修复故障“

😏工作依赖

BPDU：

  • 选根桥
  • 选端口角色
  • 监控拓扑变化

BPDU 是生成树协议中的控制报文，用于交换根桥信息、路径成本和端口标识，从而完成根桥选举、端口角色确定以及拓扑变化的感知与维护，是 STP 正常工作的基础。

😸步骤（生成一棵树）

（1）选根桥CIST Root/ERPC即根交换机，交换网络中，根桥只有一个。根交换机的端口都是指定端口。

（2）除了根交换机其余都是非根交换机。

（3）确定端口角色：

  • 先确定根端口，在非根交换机上，有且只有1个。根端口为转发状态。
  • 然后确定指定端口，每条链路上只有一个。指定端口为转发状态。
  • 其余的端口均为非指定端口。

（4）端口状态

  • Blocking（阻塞状态）：端口不会接收和发送用户的数据，但是能够接收BPDU。
  • Listening（监听状态）：端口正在接收并比较BPDU，从而确定交换机角色和端口角色，15 秒（Forward Delay），参与STR计算。
  • Learning（学习状态）：端口正在学习收到的数据的源MAC地址，形成MAC地址表。
  • Forwarding（转发状态）：端口可以正常的接收和发送用户的数据包。
  • Disabled（禁用状态）：端口还没开启STP协议或者说还没连接线路，什么都干不了。

  • 根桥（Root Bridge）： 它是 BPDU 的唯一“产生者”。根桥会按照特定的时间间隔（默认 Hello Time = 2秒）周期性地主动发送配置 BPDU（Configuration BPDU）。

😃快速生成树协议RSTP的产生与优化

RSTP协议中，对 STP 进行了很多的优化：

  • 端口角色，细化

    根端口 Root，指的是非根交换机上，有且只有1个，距离根交换机最近的口；

    指定端口Designated，指的是每段链路上，，有且只有1个，距离根交换机最近的口；

    替代端口Alternate，指的是非根交换机上，有且只有1个，距离根交换机“第二近”的口；

    这种类型的端口，是“根端口”的替代品。

    如果根端口坏掉，直接将“替代端口”，升级为“根端口”。

    该端口的状态，会立刻从“Discarding”状态，进入到“Forwarding"状态。

    备份端口Backup，指的是每段链路上，有且只有1个，距离根交换机“第二近”的口；

    这种类型的端口，是“指定端口”的替代品。

    如果指定端口坏掉，直接将“备份端口”，升级为“指定端口”

    并且，该端口的状态，会立刻从“Discarding”状态，进入到“Forwarding"状态。

    边缘端口，这种类型的端口，指的是交换机上连接那些非交换机设备所使用的端口，比如PC、Server、也就是那些所谓的 Access 端口。一旦被设定为“边缘端口”，那么这些端口一旦连接网   
    线，会立刻通！

  • 端口状态，简化（少状态，减少等待）

    *learning   - 与之前相同

    *forwarding - 与之前相同

    *discarding - 丢弃，相当于之前的 禁用、侦听、阻塞

  • 引入安全特性

    根保护，当早已规划好根交换机的一个局域网接入一个比根交换机优先级更低的交换机，其它交换机就会认为，这个交换机才是根交换机，导致原本的指定端口 / 根端口角色发生变化。防止下游设备通过发送更优 BPDU 抢占根桥角色。

    BPDU保护，边缘端口本不应该收到 BPDU，一旦收到，就说明对端不是终端设备，交换机会立即将该端口关闭。

    BPDU防护

    环路防护，环路防护（Loop Guard）用于防止阻塞端口因收不到 BPDU 而错误进入转发状态，从而引发二层环路。

① 选根桥
② 对每台非根交换机：
    └─ 选 1 个 RP
③ 对每一条链路 / 网段：
    └─ 选 1 个 DP
④ 其余端口：
    ├─ 输给别的交换机 → AP
    └─ 输给自己兄弟端口 → BP

🤪Proposal / Agreement（P/A）机制

Proposal/Agreement机制简称P/A机制，其目的是使一个指定端口尽快进入Forwarding状态

根桥DeviceA和DeviceB之间新添加了一条链路。在当前状态下，DeviceB的另外几个端口p2是Alternate端口，p3是指定端口且处于Forwarding状态，p4是边缘端口。

🌹新链路连接成功后，P/A机制协商过程如下：

  1. p0和p1两个端口马上都先成为指定端口，发送RST BPDU。
  1. DeviceB的p1口收到更优的RST BPDU，马上意识到自己将成为根端口，而不是指定端口，停止发送RST BPDU。
  1. DeviceA的p0进入Discarding状态，于是发送的RST BPDU中把Proposal和Agreement置1。
  1. DeviceB收到根桥发送来的携带Proposal的RST BPDU，开始将自己的所有端口进入sync变量置位。
  1. p2已经阻塞，状态不变；p4是边缘端口，不参与运算；所以只需要阻塞非边缘指定端口p3。
  1. 各端口的synced变量置位后，p2、p3进入Discarding状态，p1进入Forwarding状态并向DeviceA返回Agreement位置位的回应RST BPDU。
  1. 当DeviceA判断出这是对刚刚发出的Proposal的回应，于是端口p0马上进入Forwarding状态。

事实上对于STP，指定端口的选择可以很快完成，主要的速度瓶颈在于：为了避免环路，必须等待足够长的时间，使全网的端口状态全部确定，也就是说必须要等待至少一个Forward Delay所有端口才能进行转发。而RSTP的主要目的就是消除这个瓶颈，通过阻塞自己的非根端口来保证不会出现环路。而使用P/A机制加快了上游端口转到Forwarding状态的速度。

问题

在 RSTP 的 P/A（Proposal / Agreement）机制中：

什么是 sync 阶段？

sync 不是“计时等待”，而是“快速收敛的安全准备动作”，触发条件：收到对端的 Proposal BPDU。
sync 阶段，本设备会把“除了即将作为根端口的那条链路之外，所有可能参与转发、可能形成环路的端口先阻塞”。（上面的第五条）保证不会出现环路

sync 完成后，Agreement 返回，这一刻两个交换机之间到底发生了什么？

DeviceA 从 p0 发 Proposal 的意思不是“我要转发了”，而是：

“我希望立刻把 p0 切到 Forwarding，

但你（DeviceB）必须先向我保证：你那边不会因为我转发而形成环路。”

所以 Proposal 是“请求安全证明”。

DeviceB 做完 sync 的标志是：

  • 所有会造成环路的非根口（比如 p3）都已进入 Discarding
  • Alternate 仍旧阻塞
  • Edge 不参与
  • 现在设备内部只剩“根端口”这条可以转发的主路径

👨🏼‍🦱边缘端口

在RSTP/MSTP里面，如果某一个指定端口位于整个网络的边缘，即不再与其他交换设备连接，而是直接与终端设备直连，这种端口叫做边缘端口。

边缘端口不参与生成树运算，可以由Disable直接转到Forwarding状态，且不经历时延，就像在端口上将生成树协议禁用。但是一旦边缘端口收到BPDU，就丧失了边缘端口属性，成为普通端口，并重新进行生成树计算，从而引起网络振荡，BPDU保护可以解决此问题。

👏🏼RSTP的保护功能

😑BPDU保护

在RSTP网络中，正常情况下，边缘端口不会收到RST BPDU，启用了BPDU保护功能后，如果有人伪造RST BPDU恶意攻击交换机，边缘端口将被Error-Down。

如图1所示，S3上将与PC相连的端口设置为边缘端口，当边缘端口接收到RST BPDU时，交换机会自动将边缘端口设置为非边缘端口，并重新进行生成树计算。当攻击者发送的RST BPDU报文中的桥优先级高于现有网络中根桥优先级时会改变当前网络拓扑，可能会导致业务流量中断。这是网络中一种简单的拒绝服务DoS（Denial of Service）攻击方式。

交换机上启动了BPDU保护功能后，如果边缘端口收到RST BPDU，边缘端口将被error-down，但是边缘端口属性不变，同时通知网管系统。交换机上会打印如下日志信息：

MSTP/4/BPDU_PROTECTION:This edged-port [port-name] that enabled BPDU-Protection will be shutdown, because it received BPDU packet!

🥶根保护

  • 由于维护人员的错误配置或网络中的恶意攻击，网络中合法根桥有可能会收到优先级更高的RST BPDU，使得合法根桥失去根地位，从而引起网络拓扑结构的错误变动。这种不合法的拓扑变化，会导致原来应该通过高速链路的流量被牵引到低速链路上，造成网络拥塞。
  • 如图2所示，DeviceA和DeviceB处于网络核心层，两者间的链路带宽为1000M，DeviceA为网络中的根桥。DeviceC处于接入层，DeviceC和DeviceA、DeviceC和DeviceB之间的链路带宽为100M。正常情况下，DeviceB和DeviceC之间的链路被阻塞。
    当DeviceD新接入DeviceC时，由于DeviceD的桥优先级高于DeviceA，此时DeviceD会被选举为新的根桥，如果两个核心交换机DeviceA和DeviceB之间的千兆链路被阻塞，会导致VLAN中的流量都通过两条100M链路传输，可能会引起网络拥塞及流量丢失。

此时可以在DeviceC连接DeviceD的端口上，配置根保护。对于启用Root保护功能的指定端口，其端口角色只能保持为指定端口。一旦启用Root保护功能的指定端口收到优先级更高的RST BPDU时，端口状态将进入Discarding状态，不再转发报文。在经过一段时间（通常为两倍的Forward Delay 30s），如果端口一直没有再收到优先级较高的RST BPDU，端口会自动恢复到正常的Forwarding状态。

Root保护功能只能在指定端口上配置生效。

😒loop保护/环路保护

在运行RSTP协议的网络中，根端口和其他阻塞端口状态是依靠不断接收来自上游交换设备的RST BPDU维持。当由于链路拥塞或者单向链路故障导致这些端口收不到来自上游交换设备的RST BPDU时，此时交换设备会重新选择根端口。原先的根端口会转变为指定端口，而原先的阻塞端口会迁移到转发状态，从而造成交换网络中可能产生环路。

如图3所示，当BP2-CP1之间的链路发生拥塞时，DeviceC由于根端口CP1在超时时间内收不到来自上游设备的BPDU报文，Alternate端口CP2放开转变成了根端口，根端口CP1转变成指定端口，从而形成了环路。

在启动了环路保护功能后，如果根端口或Alternate端口长时间收不到来自上游设备的BPDU报文时，则向网管发出通知信息（此时根端口会进入Discarding状态，角色切换为指定端口），而Alternate端口则会一直保持在阻塞状态（角色也会切换为指定端口），不转发报文，从而不会在网络中形成环路。直到链路不再拥塞或单向链路故障恢复，端口重新收到BPDU报文进行协商，并恢复到链路拥塞或者单向链路故障前的角色和状态。

交换机上会打印如下日志信息：
MSTP/4/LOOP_GUARD:MSTP process [process-id] Instance[instance-id]'s LOOP-Protection port [port-name] did not receive message in prescriptive time!

🤣防TC-BPDU攻击

STP报文的类型：

  • 配置 BPDU（Configuration BPDU）：配置 BPDU 用于“建立和维护生成树拓扑”。
    • TC BPDU 当根桥收到下游交换机的TCN BPDU后，它会评估全局情况，然后下发带有 TC 标记（Topology Change） 的配置 BPDU即TC BPDU。告知其他交换机删除MAC地址表。
      • TCA BPDU，TCA BPDU；当下游发现拓扑变化或者故障时，会一直发送TCN BPDU，上游交换机在收到 TCN 后，会在发往该下游交换机的配置 BPDU 中，将 TCA 标志位置为 1，下游交换机收到后就会停止发送TCN BPDU。实现了可靠传输，而且所有上游交换机都可以发 TCA，不只是根桥。
  • TCN BPDU（Topology Change Notification BPDU，拓扑变化通知）：TCN BPDU 用于“告诉根桥：拓扑变了”。由非根交换机向根桥发送，根桥就会在配置 BPDU 中设置 TC 位，通知全网设备加速 MAC 表老化（STP版本专属）
  • RST BPDU（Rapid Spanning Tree BPDU）：RSTP 中没有“TCN BPDU”这种独立报文，合并了 STP 的两种（根桥选举、端口角色协商（P/A 机制）、拓扑变化通知），通过 Flags 字段 区分功能。在RSTP中只有一种BPDU。RST BPDU 用一个报文，干了 STP 里两个报文的活。

交换设备在接收到TC BPDU报文后，会执行MAC地址表项和ARP表项的删除操作。如果有人伪造TC BPDU报文恶意攻击交换设备时，交换设备短时间内会收到很多TC BPDU报文，频繁的删除操作会给设备造成很大的负担，给网络的稳定带来很大隐患。

启用防TC-BPDU报文攻击功能后，在单位时间内，交换设备处理TC BPDU报文的次数可配置。如果在单位时间内，交换设备在收到TC BPDU报文数量大于配置的阈值，那么设备只会处理阈值指定的次数。对于其他超出阈值的TC BPDU报文，定时器到期后设备只对其统一处理一次。这样可以避免频繁的删除MAC地址表项和ARP表项，从而达到保护设备的目的。

  • TCN BPDU报文主要用来向上游设备乃至根桥通知拓扑变化。
  • 置位的TCA标记的配置BPDU报文主要是上游设备用来告知下游设备已经知道拓扑变化，通知下游设备停止发送TCN BPDU报文。
  • 置位的TC标记的配置BPDU报文主要是上游设备用来告知下游设备拓扑发生变化，请下游设备直接删除MAC地址表项，从而达到快速收敛的目的。

🤩MSTP多生成树协议

😾单生成树的不足

（1）部分vlan路径不通

当交换机端口规划了不同的vlan走不同的方向时，遇到了计算好的AP（下图的vlan3规划了走右边，但是出交换机的端口为AP，任何数据都不能传送）

（2）无法实现流量分担

单生成树（Single Spanning Tree）下，冗余链路只能“备而不用”，流量永远走同一条逻辑路径，无法并行分担负载。

导致：

  • 链路带宽严重浪费
  • 转发路径的性能瓶颈

（3）次级二层路径

单生成树为了防环，只允许一条逻辑路径存在，必然阻塞部分物理上更优的链路，导致数据在二层转发时走“并非最短、并非最快”的路径，这就是单生成树的“次优二层路径”问题。

🤪MSTP概述

MSTP (Multiple Spanning Tree Protocol) 通过将一个或多个 VLAN 映射到一个 实例 (Instance)，并在每个实例中独立计算生成树，解决了传统 STP/RSTP 的局限性。

关键概念

  • MSTP (Multiple Spanning Tree Protocol)
    • 本质： 一种网络协议（IEEE 802.1s）。
    • 功能： 它定义了如何将 VLAN 映射到实例、如何在域内计算多棵生成树、以及如何与传统的 STP/RSTP 互通。
    • 视角： 它是宏观的，指代整个运行机制。
  • MSTI (Multiple Spanning Tree Instance)
    • 本质： MSTP 协议内部的一个逻辑生成树计算单元。
    • 功能： 在一个 MST 域内，MSTP 可以运行多个不干扰的生成树，每一个这样的生成树就叫一个 MSTI。
    • 视角： 它是微观的，指代具体的一棵“树”。
    • 都会独立运行一套生成树算法
    • 这套算法：
      • 根桥选举
      • 根端口 / 指定端口 / 替代端口选择
      • 端口状态（Discarding / Learning / Forwarding）

👉 完全等价于“一棵 RSTP 生成树”

MST Region (域）内可以生成多棵生成树，每棵生成树都称为一个MSTI。MSTI之间彼此独立，且每个MSTI的计算过程基本与RSTP的计算过程相同

  • MSTI 之间在逻辑上彼此独立，但共享同一物理拓扑和端口资源。

😜MSTP拓展

MSTP 多生成树协议 ，实际是将多台交换机 划分成多个区域，每个区域内包含多个生成树，每个生成树对应一个实例，即MSTI，一个实例是多个vlan的集合。

交换机连接中有MAXHOB字段，规定了最大的单线连接长度（默认为7），保证快速收敛

拓展概念

1. CST (Common Spanning Tree，公共生成树)

CST 是将每一个 MST 区域（MST Region） 看作一个“大交换机”，而在这些“大交换机”之间运行的一棵生成树。将各个区域进行相连，形成的环形网络计算出来的生成树

  • 核心逻辑：无论区域内部有多少VLAN，在区域之间，CST只维护一个拓扑，确保整个网络（所有区域互联）没有环路。
  • 适用场景：连接不同的 MST 区域，或者连接MST区域与运行传统 STP/RSTP 的单生成树区域。

2. CIST (Common and Internal Spanning Tree，公共和内部生成树)

这是整个网络中级别最高的树。它是 CST + 所有区域内 IST 的总和。

  • 核心逻辑：它是一个覆盖全网的逻辑单生成树，计算出全网的“总根”（CIST Root）。
  • 作用：它确保了无论网络划分了多少个区域，在逻辑上整张网都有一个统一的防环底座。

3. IST (Internal Spanning Tree，内部生成树)

IST 是 CIST 在某个特定 MST 区域内部的延伸。

  • 核心逻辑：在一个 MST 区域内，默认存在 Instance 0，这个 Instance 0 就是 IST。
  • 作用：它负责在该区域内部传递由 CIST 派发的生成树信息，并将该区域内的所有交换机连通。你可以把它理解为 CIST 在该区域内的“本地代理”。
  • 一个区域内有多个实例，一个实例就是一个MSTI，其中实例0是特殊的一个MSTI，称为IST。

4. MSTI (Multiple Spanning Tree Instance，多生成树实例)

这是 MSTP 真正实现负载分担的核心。

  • 核心逻辑：在同一个 MST 区域内，管理员可以手动创建多个实例（如 Instance 1, Instance 2），并将不同的 VLAN 映射到不同的实例中。
  • 作用：
    • Instance 1 可以以交换机 A 为根，阻塞某条链路。
    • Instance 2 可以以交换机 B 为根，阻塞另一条链路。
  • 结果：不同 VLAN 的流量走不同的物理路径，解决了老式 STP 只有一棵树、导致部分链路闲置的问题。

5、总根（CIST Root） 是指整棵 CIST（公共和内部生成树） 的根桥。（整个网络的交换机里优先级最高的）

6、主桥（master）是指在某个 MST 区域内，距离总根（CIST Root）最近的那台交换机。

  • 如果总根在区域内部：那么总根自己就是该区域的主桥。
  • 如果总根在区域外部：该区域内到总根路径开销（Cost）最小的交换机就是主桥。

RSTP端口角色有：

二层可靠性除了生成树协议还有：链路聚合、堆叠。

  • 链路聚合
    • 多条流量会被分配到不同的物理链路上并发转发，而同一条流量始终固定走一条物理链路；当某条链路故障时，其余链路仍可承载业务，保证整体通信不中断。
    • 链路故障切换过程（Failover）
      1. 物理感应：一根物理线 Down，在途报文丢失（瞬时丢包）。
      1. 逻辑剔除：LACP/Eth-Trunk 迅速将该成员口从转发组中移除。
      1. 重新 Hash：后续报文（Flow）根据源/目 IP 重新映射到剩余的 Up 链路上。
      1. 业务连续：依靠 TCP 重传机制，业务会话保持，用户无感知。
  • 堆叠
    • 堆叠技术通过虚拟化技术将多台物理交换机整合成一个逻辑整体，消除了设备间的协议差异与环路风险，配合跨设备链路聚合，实现了网络从链路级到设备级的全方位冗余与无感切换。
  • 逻辑层：整个堆叠组表现为一台逻辑交换机。
    • 统一的管理 IP。
    • 统一的配置文件（Config）。
    • 统一的生成树 Bridge ID。
  • 解决“单点故障”带来的业务中断风险
    • 传统的冗余（如 VRRP）虽然能解决网关备份，但切换速度和配置复杂度较高。
    • 痛点：核心交换机整机宕机时，业务切换可能导致长达数秒甚至分钟级的抖动。
    • 解决：堆叠建立了控制平面的实时同步。
    • 结果：主交换机（Master）挂了，备交换机（Standby）瞬间接管。因为协议状态（如 OSPF 邻居、MAC 表）是同步的，业务切换通常在 ms（毫秒）级，用户几乎无感知。
  • 解决“海量设备”带来的管理负担随着业务扩张，接入层交换机可能多达数十台。
    • 痛点：你需要记几十个管理 IP，维护几十份配置文件，升级系统要跳几十台设备。
    • 解决：堆叠将多台物理机虚拟化。
    • 结果：“多变一”。你只需要登入一个 IP，改一份配置，全堆叠组同步生效。这极大地降低了人工操作导致配置不一致（Config Mismatch）的概率。=

⚠️解决办法——VRRP


VRRP（Virtual Router Redundancy Protocol，虚拟路由器冗余协议）的核心原理是将多台物理路由器组合成一个虚拟路由器（Virtual Router），对外表现为一个共同的“虚拟网关”。

🤤关键概念

VRRP虚拟路由器：

运行VRRP协议的路由器，VRRP配置在路由器的接口上，而且也是基于接口工作的。

VRID：

一个VRRP组由多台协同工作的路由器组成，使用相同的VRID进行标识。属于同一个VRRP组的路由器之间交互VRRP报文并产生一台虚拟的路由器

虚拟IP地址及虚拟MAC地址：

虚拟路由器拥有自己的IP地址以及MAC地址，其中IP地址由网络管理员在配置VRRP时指定，一台虚拟路由器可以有一个或多个IP地址，通常情况下用户使用该地址作为网关地址。而虚拟MAC地址的格式是“0000-5e00-01xx”，其中xx为VRID。

MASTER路由器（主路由器）：

在一个VRRP组中承担报文转发任务。在每一个VRRP组中，只有Master路由器才会响应针对虚拟IP地址的ARP Request。Master路由器会以一定的时间间隔周期性地发送VRRP报文，以便通知同一个VRRP组中的Backup路由器关于自己的存活情况。（默认每隔一秒发）

Backup路由器：

也被称为备份路由器。Backup路由器将会实时侦听Master路由器发送出来的VRRP报文，它随时准备接替Master路由器的工作。（三倍Master发报文间隔的时间就会启用备份路由器）

Priority：

优先级值是选举Master路由器和Backup路由器的依据，优先级取值范围0-255，值越大越优先，值相等则比较接口IP地址大小，大者优先。默认值为100

    当前实际生效的优先级

  • PriorityConfig

    人工配置的基础优先级。

    取值范围：1–255

    默认值：100

    不受运行状态影响，仅作为初始值。

  • Preempt
    • YES：开启抢占
      • 高优先级设备恢复后可重新成为 Master。
    • NO：关闭抢占
      • 一旦 Master 确立，除非其故障，否则不发生切换。
  • Delay Time
    • 抢占延时。
  • Virtual MAC
    • VRRP 使用的虚拟 MAC 地址。
  • Auth type
    • NONE：无认证（最常见）。
    • SIMPLE：简单明文认证（已不推荐）。
    • MD5（部分型号支持）：报文完整性校验。
    • 用于防止非法 VRRP 报文注入。
    • NONE：
      “只要你说你是 VRRP 1，我就信你”
    • SIMPLE：
      “你得对上暗号，但暗号是明文写在纸上的”
    • MD5：
      “你得用正确的密钥算出验证码，我才信你”

😃VRRP抢占模式（Preempt Mode）

-抢占模式（默认激活）：如果Backup路由器激活了抢占功能，那么当它发现Master路由器的优先级比自己更低时，它将立即切换至Master状态，成为新的Master路由器
-非抢占模式：如果Backup路由器没有激活抢占功能，那么即使它发现Master路由器的优先级比自己更低，也只能依然保持Backup状态，直到Master路由器失效。

关闭抢占模式：vrrp vrid num preempt-mode disable

🥵VRRP认证

提高安全性和可靠性，主要提高的是报文的可靠性 。-通告报文

认证配置必须要在参与 VRRP 的接口视图下配置，也就是说主备网关接口

VRRP 组内只要认证配置不一致，收到的 VRRP 报文就会被直接丢弃，等价于“没收到”，结果就是出现多个 Master。

认证的分类

  • simple 只能在CLI的查看（display vrrp/display this→在接口）中有区别，在抓包的时候都能看到认证字符
    • plain：明文储存，可以直接查看
    • cipher：密文，设置之后再CLI只能查看到乱码符好

由于plain和cipher只影响本地储存，只要两者设置的内容一样，即使一个端口是plain一个是cipher也能正常接受报文（两端配置本地加密算法不一致，不影响VRRP 两端的状态）

  • MD5，和simple的cipher不一样的是，在抓包的时候，不能看到密令。
    • 出现MD5和simple的混用（一边simple一边MD5），报文会丢弃

😧DHCP 与 UDP 的关系总结

  • DHCP 是 应用层协议，运行在 UDP 之上
  • DHCP 使用 UDP 67（Server） / 68（Client）
  • 客户端初始阶段 没有 IP、没有服务器地址
  • UDP 无连接、无需三次握手
  • UDP 支持广播，满足 DHCP Discover/Request 的通信需求
  • DHCP 通过 超时重传机制 而非 TCP 可靠性保证成功

😶C/S的通信模式

DHCP 采用 Client / Server（C/S）模型

Client：终端设备（PC、手机、打印机等）。主动发起服务请求，接收配置结果

Server：集中分配地址与参数的设备。维护地址池，决定地址分配。

🤠工作原理（DHCP客户端首次接入）

DORA四个阶段

1）发现阶段Discovery

DHCP客户端发现DHCP服务器的阶段。

- DHCP客户端发送DHCP DISCOVER报文来发现DHCP服务器。DHCP DISCOVER报文中携带了客户端的MAC地址、需要请求的参数列表选项、广播标志位等信息。

客户端发送的是广播包，客户端尚无 IP，只能广播。在同一广播域内寻找 DHCP 服务器

DHCP DISCOVER报文内容：

  • 客户端 MAC 地址（Client Hardware Address）
  • 事务 ID（XID）
  • DHCP 报文类型：DISCOVER（Option 53）
  • 参数请求列表（Option 55，如网关、DNS）
  • 客户端标识（Option 61，可选）
  • 广播标志位（Broadcast Flag）

2）提供阶段OFFER

即DHCP服务器提供网络配置信息的阶段。

- 服务器接收到DHCP DISCOVER报文后，选择跟接收DHCP DISCOVER报文接口的IP地址处于同一网段的地址池，并且从中选择一个可用的IP地址，然后通过DHCP OFFER报文发送给DHCP客户端。

DHCP OFFER报文内容：

  • 拟分配的 IP 地址（Your IP Address），不能用，未建立租约
  • 子网掩码
  • 默认网关
  • DNS 服务器
  • 租期时间
  • DHCP 报文类型：OFFER（Option 53）
  • 服务器标识（Option 54）
  • 事务 ID（XID）（与 DISCOVER 对应）

3）选择阶段Request

DHCP客户端选择IP地址的阶段。

- 如果有多个DHCP服务器向DHCP客户端回应DHCP OFFER报文，则DHCP客户端一般只接收第一个收到的DHCP OFFER报文，然后以广播方式发送DHCP REQUEST报文，该报文中包含客户端想选择的DHCP服务器标识符和客户端IP地址。

为什么要广播发送DHCP REQUEST报文？
告知未选中的服务器，释放预留IP

告知选中服务器，继续后面的流程

基础字段

  • Message Type：DHCPREQUEST（Option 53 = 3）
  • Client MAC Address：客户端物理地址
  • Transaction ID（XID）：事务标识，用于匹配请求/响应
  • Flags：广播/单播标志（常见为广播）
  • Client IP Address（ciaddr）
    • 续租/重绑定阶段可能填写
    • 初次获取通常为 0.0.0.0

关键选项（Options）

  • Requested IP Address（Option 50）：客户端请求使用的 IP（通常来自 OFFER）
  • Server Identifier（Option 54）：被选中的 DHCP 服务器 IP
  • Parameter Request List（Option 55）：请求的配置参数列表
    • 常见：子网掩码、默认网关、DNS、域名、MTU 等
  • Client Identifier（Option 61）：客户端标识（可能是 MAC 或其他 ID）
  • Hostname（Option 12）（可选）：主机名
  • Lease Time（Option 51）（可选）：期望租期
  • Relay Agent Information（Option 82）（可选）：中继信息（有 DHCP Relay 时）
DHCPREQUEST 用于确认选择的 DHCP 服务器与 IP 地址，并正式申请该地址的使用权。即请求获取的参数

4）确认阶段ACK

DHCP服务器确认所分配IP地址的阶段。

- DHCP客户端收到DHCP ACK报文，会广播发送免费ARP报文，探测本网段是否有其他终端使用服务器分配的IP地址。

收到ACK报文之后，设备正式能使用ACK报文。

ACK报文的字段内容

op      = 2              // BOOTREPLY
xid     = 事务ID         // 与Discover一致
yiaddr  = 分配的IP地址   // 客户端最终获得的IP
siaddr  = DHCP服务器IP
chaddr  = 客户端MAC地址
Option 53 = 5            // DHCP Message Type = ACK
Option 54 = 服务器标识   // DHCP Server Identifier
Option 51 = 租期时间     // Lease Time
Option 1  = 子网掩码

Option 6  = DNS服务器
Option 58 = T1           // 续租时间

阶段报文类型发送方 → 接收方作用
1DHCP DiscoverClient → Broadcast寻找可用 DHCP 服务器
2DHCP OfferServer → Client提供拟分配 IP
3DHCP RequestClient → Broadcast选择某一服务器并申请该 IP
4DHCP AckServer → Client确认分配，正式生效

如果不是首次接入，应该如何操作？

租期未过期：直接进入请求阶段request，Client → 单播 DHCP REQUEST → 原服务器

服务器返回DHCP ACK（第四阶段确认阶段），然后IP不变租期重置，不广播。

租期过期：直接进入DORA

Secs（seconds）：由客户端填充，表示从客户端开始获得IP地址或IP地址续租后所使用了的秒数，缺省值为3600s。

Flags：客户端请求服务器发送响应报文的形式，只有最高位有意义，其余15位置0。最高位为0时请求发送单播响应，最高位为1时请求发送广播响应

Yiaddr（your client ip address）：表示服务器分配给客户端的IP地址。当服务器进行DHCP响应时，将分配给客户端的IP地址填入此字段。

Siaddr（server ip address）：DHCP服务器的IP地址

Chaddr（client hardware address）：客户端的MAC地址

Options：DHCP通过此字段包含了服务器分配给终端的配置信息。

🫤DHCP消息类型

消息类型的内容在options的| 53 | 1 | Message Type

1-DHCP DISCOVER：DHCP客户端首次登录网络时进行DHCP交互过程发送的第一个消息，用来寻找DHCP服务器。


2-DHCP OFFER：DHCP服务器用来响应DHCP DISCOVER消息，此消息携带了各种配置信息。


3-DHCP REQUEST：DHCP客户端广播请求回应DHCP服务器OFFER消息；DHCP客户端重启广播确认之前的IP地址等配置信息；续租。


4-DHCP DECLINE：当客户端发现服务器分配给它的IP地址发生冲突时会通过发送此消息来通知服务器。


5-DHCP ACK：DHCP服务器对客户端的DHCP REQUEST消息的确认响应消息。


6-DHCP NAK：服务器对客户端的DHCP REQUEST消息的拒绝响应消息。


7-DHCP RELEASE：客户端可通过发送此消息主动释放服务器分配给它的IP地址。


8-DHCP INFORM：DHCP客户端获取IP地址后，如果需要向DHCP服务器获取更为详细的配置信息（网关地址、DNS服务器地址），则向DHCP服务器发送DHCP INFORM请求消息。

😋地址续租

DHCP客户端根据IP地址的剩余租期的不同而产生不同形式的续租请求。

  • 当租期达到50%（T1）时，DHCP客户端会自动以单播的方式向DHCP服务器发送DHCP REQUEST报文，请求更新IP地址租期。如果收到DHCP服务器回应的DHCP ACK报文，则租期更新成功。
  • 当租期达到87.5%（T2）时，如果仍未收到DHCP服务器的应答，DHCP客户端会自动以广播的方式向DHCP服务器发送DHCP REQUEST报文，请求更新IP地址租期。如果收到DHCP服务器回应的DHCP ACK报文，则租期更新成功。
  • 如果租期时间到时都没有收到服务器的回应，客户端停止使用此IP地址，重新发送DHCP DISCOVER报文请求新的IP地址。

💜DHCP中继

😮‍💨作用

DHCP中继（DHCP Relay）用于解决 DHCP 广播不能跨越路由器的问题，使不同网段的主机能够通过远程 DHCP 服务器自动获取 IP 地址参数。这样可以在网络中只部署一台 DHCP 服务器，由该服务器统一为多个网段分配 IP 地址，实现地址分配的集中管理。

工作原理

客户端首次获取地址时会发送 DHCP Discover 广播报文（目的地址 255.255.255.255）。由于广播报文不能通过路由器转发，位于其他网段的 DHCP 服务器无法直接收到该请求。当路由器接口配置了 DHCP 中继功能后，它会接收客户端的广播请求，并将该报文转换为单播报文转发给指定的 DHCP 服务器，同时在报文中填入 giaddr（网关地址）字段，用来标识客户端所在的网段。 DHCP 服务器根据 giaddr 判断客户端所属网络，并从对应地址池中分配 IP 地址，然后将响应报文返回给中继设备，中继设备再将该响应转发给客户端，最终完成 DHCP 的地址获取过程。

dns-list 8.8.8.8

🥰DHCPsnooping简介

😶‍🌫️由来

  • 无身份认证机制
  • 基于广播通信
  • 客户端信任网络中的DHCP服务器

交换机无法判断：

哪个是合法 DHCP Server
哪个是非法 DHCP Server

因此网络中出现大量安全问题。

DHCP攻击，往往源于“私接设备”，而这些“私接设备”，往往又是通过“接入层交换机”，接入到企业网络内部的

所以，虽然DHCP Snooping功能是针对应用层协议DHCP的安全防范，但是它的配置位置，都是在“接入交换机”

🦻🏼概述

定义：

DHCP snooping 是DHCP的的一种安全特性，用于保证DHCP客户端从合法的DHCP服务器获取IP地址，并记录DHCP客户端IP地址与MAC地址等参数的对应关系，防止网络上针对DHCP攻击（类似于在客户端和DHCP服务器之间建立了一个防火墙）

核心思想：

  • 交换机 监听（Snoop）DHCP报文
  • 识别 可信端口 / 非可信端口
  • 只允许 合法 DHCP Server 的报文进入网络

😡Snooping的开启

[ 1 ]在系统视图下敲：dhcp enable //开启DHCP服务

[ 2 ]在系统视图下敲：dhcp snooping enable //开启DHCP窥探功能

[ 3 ]在接口或VLAN视图下敲：dhcp snooping enable，在接口敲：为该接口开启DHCP窥探功能在VLAN视图下敲：为该VLAN所包含的所有接口开启DHCP窥探功能

🫠Snooping端口角色简介

端口角色含义允许通过的 DHCP 报文典型位置
Trusted Port（信任端口）被交换机认为是可信的端口允许所有 DHCP 报文通过（Discover / Offer / Request / ACK）连接 DHCP服务器、DHCP中继、上联交换机
Untrusted Port（非信任端口）默认状态，认为不可信只允许客户端报文（Discover / Request）通过，禁止服务器报文（Offer / ACK）连接 PC、终端、接入设备

作用：防止仿冒 DHCP Server（DHCP 私接）向客户端发送 Offer/ACK。
把 连接 DHCP Server 的接口 设置为 Trusted

🤤常见攻击和防范

😑1、DHCP Server仿冒者攻击与防范

指攻击者在网络中 私自接入一个 DHCP 服务器，向客户端分配 错误的网络参数（IP、网关、DNS 等）。客户端因为 先收到谁的 DHCP Offer 就使用谁的地址，因此可能被伪造服务器抢先响应。

能够仿冒DHCP服务器的设备，都会出现在“接入层设备”下连的网络中,即：设备私接的接口，都是“接入层设备”的接口

而DHCP中继是不需要配置“防范DHCP Server仿冒者攻击”的，因为中继通过“dhcp server-ip x.x.x.x”命令，已经明确知道了“谁是DHCP服务器”

🤏🏼防范原理：trusted和untrusted端口

1 客户端请求报文

客户端发送：

DHCP Discover
DHCP Request

交换机允许从 非信任端口进入，并转发到 信任端口（DHCP服务器方向）。

2 服务器应答报文

服务器返回：

DHCP Offer
DHCP ACK

交换机只允许 从信任端口进入的应答报文。

如果 非信任端口收到 Offer / ACK：

直接丢弃

步骤

  1. 先开启 DHCP Snooping 基本功能
  1. 配置信任端口（Trusted Port）

[SW]interface GigabitEthernet0/0/1
[SW-GE0/0/1]dhcp snooping trusted

方式二：VLAN 视图配置

🥱2、DHCP 报文泛洪攻击与防范

DHCP 报文泛洪攻击是指攻击者在短时间内向 DHCP 服务器发送大量 DHCP 请求报文（Discover、Request），通常还会伪造大量不同的 MAC 地址，不断向服务器申请 IP 地址，使服务器持续处理这些请求。

😋造成的后果

1 地址池耗尽

攻击者不断申请IP地址，服务器为每个伪造的 MAC 地址分配地址，最终导致DHCP地址池被占满，正常客户端无法再获取IP地址。

2 DHCP 服务器处理能力耗尽

服务器需要对每个 DHCP 请求进行解析、地址分配和租约记录。当请求数量过多时，DHCP 报文处理单元无法及时处理所有请求，导致 DHCP 服务变慢甚至无法正常工作。

DHCP 泛洪攻击是伪装成DHCP客户端发起的攻击，而客户端在DHCP过程中能够主动发送的报文主要是：

DHCP Discover
DHCP Request

👱🏼‍♀️防范原理：

在“接入层设备限制DHCP请求报文的速率，如果设备接收到的报文，超过了我们设置的阈值，超过的部分就会被丢弃

配置命令

  • 配置位置：
    • 1. 系统视图下配置，针对全局有效
    • 2. VLAN视图下配置，针对该VLAN内所有接口有效
    • 3. 接口视图下配置，针对该接口有效
  • 配置阙值的取值以及注意事项：
    • 配置的位置：
      • 1. 系统视图下配置，针对全局有效
      • 2. VLAN视图下配置，针对该VLAN内所有接口有效
      • 3. 接口视图下配置，针对该接口有效
      • 4. 如果三者都配置，取我们设定的速率阈值的最小值

😐3、仿冒DHCP报文攻击与防范

概述：

1）仿冒request报文

DHCP中的REQUEST报文的作用是：

  1. 客户端在收到服务器的OFFER后，进行广播的REQUEST报文发送，请求指定的服务器提供IP地址等参数，同时拒绝其他服务器
  1. 在IP地址租期到达50%时，客户端发送单播的REQUEST报文，请求续租
  1. 在IP地址租期到达87.5%时，客户端发送广播的REQUEST报文，请求续租
如果攻击者，仿冒的REQUEST报文到达服务器，就意味着服务器本来可以“回收”的IP地址，又被“错误”的续期了

🚫服务器就会认为该客户端依旧使用着这个IP地址（即使该地址没有被使用也会被占用）

2)仿冒release报文

DHCP中的RELEASE报文的作用是：

客户端主动释放 IP：

ipconfig /release

服务器：

删除租约 → IP回收
如果攻击者持续发送仿冒合法用户的RELEASE报文，就会导致“合法用户”的IP地址被“错误的释放”

导致客户端的终端上网参数被强制释放，设备不能上网。

👺防范原理：

首先先讲解一下DHCP Snooping绑定表

实际上是一张动态生成的合法用户映射表，典型字段如下（交换机监听ACK报文提取信息）

MAC地址、IP地址、VLAN ID、接口（Interface）、租约时间（Lease）

注意只有成功分配的信息才会保存在该表中

1）request

  • 首先查看数据帧的头部，目的MAC地址是否为全F，如果是就放行
    • 因为这个报文，要么是客户端首次申请IP地址的报文，要么是客户端租期到达87.5%时发送的广播报文
  • 如果不是全F则查看DHCP Snooping绑定表，各个字段的值进行匹配，如果能够全部匹配成功则放行，不行的话就丢弃
  • 查看DHCP报文中的Chaddr字段（客户端的MAC地址）
    • 如果“DHCP Snooping绑定表”中没有相关表项
      • 说明客户端首次申请IP地址，直接放行
    • 如果“DHCP Snooping绑定表”中有相关表项
      • 查看表项是否匹配，匹配则放行，否则丢弃

2）release

查看报文是否匹配了“DHCP Snooping绑定表”，匹配则放行，否则丢弃

如果攻击者伪造REQUEST报文时，设计的二层头部目的MAC地址是全F，并且，DHCP报文内容中的“Chaddr”字段不断变化，攻击者就可以逃脱“DHCP Snooping绑定表”的检查

所以，我们需要检查DHCP请求报文中的二层头部源MAC和DHCP报文中的“Chaddr”字段是否相同

相同则放行，不同则丢弃

命令配置：
启用匹配DHCP Snooping绑定表

即：

所有DHCP REQUEST/RELEASE 报文

必须匹配 DHCP Snooping绑定表

命令→系统视图

dhcp snooping check dhcp-request enable vlan 10
dhcp snooping check dhcp-request enable vlan 10 to 20

→VLAN/接口视图

dhcp snooping check dhcp-request enable

开启检查数据帧二层头部源MAC与DHCP报文Chaddr字段是否相同的功能

系统视图下→

dhcp snooping check dhcp-chaddr enable vlan 10
dhcp snooping check dhcp-chaddr enable vlan 10 to 20

VLAN/接口视图→

dhcp snooping check dhcp-chaddr enable

查看DHCP绑定表→

ip dhcp snooping binding

强制要求：
二层源MAC == DHCP报文中的Chaddr

😐4、DHCP Server 服务拒绝攻击与防范（Dos）

概述：

DHCP服务器分配IP地址的时候，只会查看DHCP请求报文中的Chaddr字段（客户端的MAC地址字段）只要Chaddr字段不同，就认为是不同的客户端申请IP地址，攻击者会伪造DHCP请求报文，报文中的Chaddr字段不断变化

DoS攻击 = Denail of Service = 拒绝服务攻击
通过伪造“客户端身份”，耗尽地址池资源

危害

DHCP服务器的地址池资源枯竭，无法再为合法用户提供IP地址等参数

即：服务器会“拒绝”合法用户的IP地址请求

💜防范：

1）针对攻击者发送的海量DHCP请求报文，我们可以限制学习到的DHCP Snooping绑定表表项的个数说白了，就是限制DHCP最大的用户数量，一旦用户数超过我们配置的值，多出来的用户就无法申请到IP地址等参数（即使这个地址池还有剩余的地址，如果绑定表满了就不会再分配）

2）攻击者不断变换DHCP报文中的Chaddr字段，假装是多个用户申请IP地址，我们也可以检查DHCP请求报文的二层头部源MAC 和 DHCP报文中的Chaddr字段是否相同。

配置命令：

限制DHCP Snooping绑定表的个数

dhcp snooping max-user-number 绑定表个数

🤪ACL访问控制列表

😶‍🌫️概述

💔背景

随着网络的飞速发展，网络安全和网络服务质量QoS（Quality of Service）问题日益突出。园区重要服务器资源被随意访问，园区机密信息容易泄露，造成安全隐患。

Internet病毒肆意侵略园区内网，内网环境的安全性堪忧。网络带宽被各类业务随意挤占，服务质量要求最高的语音、视频业务的带宽得不到保障，造成用户体验差。
以上种种问题，都对正常的网络通信造成了很大的影响。因此，提高网络安全性和服务质量迫在眉睫，我们需要对网络进行控制。比如，需要借助一个工具帮助实现一些流量的过滤。

即：流量过滤

就如，在一个公司中，总裁可以访问财务部的服务器但是研发部门不允许访问。

🙎🏼‍♂️简介/组成

ACL是由一系列permit或deny语句组成的、有序规则列表。

是一个匹配工具，能够对报文进行匹配和区分。

每条语句就是该ACL的一条规则，每条语句中permit或deny就是雨这条规则对应的处理动作

1）ACL number 标识和区分不同ACL的唯一数字，代表一个独立的 ACL列表。每个ACL编号对应着一组规则（条目），这些规则用于过滤特定条件下的网络流量。

2）规则编号 (rule 5, rule 15, rule 20, rule 4294967294)：用于标识ACL规则。可以自行配置规则编号，也可以由系统自动分配。ACL规则的编号范围是0～4294967294，所有规则均按照规则编号从小到大进行排序。系统按照规则编号从小到大的顺序，将规则依次与报文匹配，一旦匹配上一条规则即停止匹配。

另外，每条规则编号之间都会有适当的步长，这是因为为后面插入新的规则预留空间。

3）动作：permit和deny，分别表示允许和拒绝。

4）source源地址：

  • 表示规则匹配的源地址。
  • 比如，source 1.1.1.0 0.0.0.255 表示匹配源地址范围从 1.1.1.0 到 1.1.1.255（0.0.0.255 是反向掩码）。

5）反向掩码：

反向掩码的每一位与 IP 地址的每一位进行比较时：

  • 0 表示该位置必须完全匹配（即要求该位相同）。
  • 1 表示该位置可以忽略（即该位不做匹配检查，可以是任何值）

通常是正常掩码的取反计算得来的

source 192.168.1.0 0.0.0.255 代表192.168.1.x部分必须相同，而后面的范围是0 到 255 之间的任何值。

6）时间范围 (time-range time1)：

  • 这表示规则适用的时间范围。只有在时间范围 time1 之内，这条规则才会生效。

7）隐含规则：通常存在于末尾，是ACL 配置中默认存在的、但并未显式列出的一条规则。作用是隐含的拒绝，当数据包在经过上面的规则依旧没匹配到定义好的规则就会被隐含规则拒绝，deny all

（根据调用场景不同，隐含规则不同）

8）通配符：

  • 反向掩码 (Inverse Mask) 反转子网掩码并严格遵循子网掩码的连续性，0 表示匹配，1 表示忽略。它通常用于路由协议中，标识整个网络地址范围。计算时，反向掩码不允许有间隔，必须是连续的。
  • 通配符掩码 (Wildcard Mask) 通常用于 ACL、OSPF 等协议，虽然大部分情况下也表现为反转子网掩码，但它允许 0 和 1 不连续。这使得它能够实现更复杂的匹配模式，比如精确匹配某些地址段的奇数或偶数 IP 地址。
  • 两者都为32位

😶通配符奇数匹配

由于奇数IP地址的最后一位总是1，所以为了在该网段匹配奇数IP地址，除了网络位要严格匹配，奇数上还要要求通配符最后一位为0，匹配该项才是奇数，其余位可以随意，则0.0.0.254

划分如下：

  • 数字型ACL：传统的ACL标识方法。创建ACL时，指定一个唯一的数字标识该ACL。
  • 命名型ACL：通过名称代替编号来标识ACL。

😴匹配机制

遵循“一旦命中即停止匹配”的机制

首先系统会查找设备上是否配置了ACL。

  • 如果ACL不存在，则返回ACL匹配结果为：不匹配。
  • 如果ACL存在，则查找设备是否配置了ACL规则。
    • 如果规则不存在，则返回ACL匹配结果为：不匹配。
    • 如果规则存在，则系统会从ACL中编号最小的规则开始查找。
  • 如果匹配上了permit规则，则停止查找规则，并返回ACL匹配结果为：匹配（允许）。
  • 如果匹配上了deny规则，则停止查找规则，并返回ACL匹配结果为：匹配（拒绝）。
  • 如果未匹配上规则，则继续查找下一条规则，以此循环。如果一直查到最后一条规则，报文仍未匹配上，则返回ACL匹配结果为：不匹配。

从整个ACL匹配流程可以看出，报文与ACL规则匹配后，会产生两种匹配结果：“匹配”和“不匹配”。

  • 匹配（命中规则）：指存在ACL，且在ACL中查找到了符合匹配条件的规则。

    不论匹配的动作是“permit”还是“deny”，都称为“匹配”，而不是只是匹配上permit规则才算“匹配”。

  • 不匹配（未命中规则）：指不存在ACL，或ACL中无规则，再或者在ACL中遍历了所有规则都没有找到符合匹配条件的规则。

    以上三种情况，都叫做“不匹配”

🤢匹配顺序

  • 规则编号顺序：系统会按照规则编号从小到大的顺序进行匹配。也就是说，编号越小的规则越先被匹配。
  • 显式规则匹配：当报文到达时，系统会按照ACL中配置的规则顺序检查报文的各项特征（如源 IP 地址、目的 IP 地址、协议类型等）。如果规则匹配成功，报文会根据该规则的动作（如 permit 或 deny）被处理。
  • 基于这种匹配顺序，所有规则都要从严到松配置。

🤫配置顺序

配置顺序，即系统按照ACL规则编号从小到大的顺序进行报文匹配，规则编号越小越容易被匹配。

  • 如果配置规则时指定了规则编号，则规则编号越小，规则插入位置越靠前，该规则越先被匹配。
  • 如果配置规则时未指定规则编号，则由系统自动为其分配一个编号。该编号是一个大于当前ACL内最大规则编号且是步长整数倍的最小整数，因此该规则会被最后匹配。（仅配置了规则没有配置编号）

😁匹配位置

1. 进站（Inbound）流程

  • 检查接口方向是否应用 ACL：首先判断是否在接口上应用了进站（Inbound）方向的 ACL。
    • 如果 没有 应用 ACL，则数据包会经过路由处理。
    • 如果 应用了 ACL，系统继续检查 ACL 是否允许该数据流通过。
  • ACL 允许流量吗？：
    • 如果 允许，数据包继续传递。（与路由表匹配，查看路由条目）
    • 如果 不允许，数据包会被丢弃。

2. 出站（Outbound）流程

是否有匹配的路由条目：检查是否有匹配的路由条目。

  • 如果 没有 匹配路由条目，数据包会被丢弃。
  • 如果 有 匹配的路由条目，继续判断出站方向的 ACL。

检查出站方向是否应用 ACL：如果 ACL 应用在出站方向，系统继续判断是否允许该流量。

  • 如果 允许，数据包继续发送出去。
  • 如果 不允许，数据包会被丢弃。

😁动态NAT

👽概述

提出了公有地址池的概念：所可用公有地址组成地址池。当内部主机访问外部网络时临时分配一个地址池中未使用的地址，并标记改地址“in use”;当该主机不在访问外部网络时回收分配的地址，重新标记为“not use”(这样就不会像静态nat占用公有地址但是不使用的情况)

假设地址池有n个地址，那同一时间内，只能给n个内部设备进行NAT转换。

本质上并不节省公有地址

🤪工作原理/流程

1）首先，内网设备向外网发送数据包，源IP为私有地址，目标IP为公有地址，经过NAT设备，在地址池中的空闲公有地址随机分配给这个数据包，作为源IP地址。

2）并且形成一个NAT映射表私有地址—————公有地址 ，接着该数据包就会带着分配的公有地址向外网发送。

3）接着数据包返回，原本的公有地址变为目标IP，原本的目标IP变为源IP地址。到达NAT设备后，查看NAT映射表，将目标地址释放，转换为原本的私有IP地址。

4）查看路由表和二层的表，进行转发，发送回原来的内部设备

🥴配置命令

1）创建地址池

配置公有地址范围，其中group-index为地址池编号，start-address、end-address分别为地址池起始地址、结束地址。

[Huawei] nat address-group group-index start-address end-address 

2）配置ACL

配置基础ACL，匹配需要进行动态转换的源地址范围。（精确匹配需要转换的流量，不然所有流量经过都会转换）

[Huawei] acl number 
[Huawei-acl-basic-number] rule permit source source-address source-wildcard

3）接口视图下配置地址池的NAT Outbound

接口下关联ACL与地址池进行动态地址转换，no-pat参数指定不进行端口转换。

[Huawei-GigabitEthernet0/0/0] nat outbound acl-number address-group group-index [ no-pat ]

🤨NAPT

概述

动态NAT 本质上并不节省公有地址。同一时刻，公有地址池里有几个公有地址，就支持几个私有主机上网

动态NAT选择地址池中的地址进行地址转换时不会转换端口号，即No-PAT（No-Port Address Translation，非端口地址转换），公有地址与私有地址还是1:1的映射关系，无法提高公有地址利用率。

NAPT（Network Address and Port Translation，网络地址端口转换）：从地址池中选择地址进行地址转换时不仅转换IP地址，同时也会对端口号进行转换，从而实现公有地址与私有地址的1:n映射，可以有效提高公有地址利用率。

对比项动态 NATNAPT
转换内容只改源 IP改源 IP + 源端口
公网地址占用方式一台内网主机通常占一个公网 IP多台内网主机可共用一个公网 IP
地址利用率低高
适用场景公网地址较充足公网地址紧张，最常用
华为配置区别带 no-pat不带 no-pat

实质上只需要在动态NAT的基础上删除no pat

😉Easy IP

😑概述

Easy IP:实现原理和NAPT相同,同时转换IP地址、传输层端口,区别在于Easy IP没有地址池的概念,使用出接口地址作为NAT转换的公有地址。

Easy IP适用于不具备固定公网IP地址的场景:如通过DHCP、PPPoE拨号获取地址的私有网络出口,可以直接使用获取到的动态地址进行转换。

即私有地址可以同时使用出接口的公有IP地址上网，但是其实实际上端口不一样。

😑NAPT和Easy IP的区别

相同点

  • 都属于：NAPT（端口地址转换）
  • 都支持：多个私网主机共享公网IP
  • 都依赖：端口号区分连接
  • 转换形式一致：
私网IP:端口  ⇄  公网IP:端口
  • 都需要 ACL 指定匹配流量
  • 都在出接口方向生效

不同点

公网地址来源

  • Easy IP
    → 直接使用出接口IP
  • NAPT
    → 使用地址池（nat address-group）

公有地址数量：

  • Easy ip只有一个公有地址
  • NAPT可以有多个

🤧步骤三（内外网互联）

需求：

-多 VLAN 业务隔离（财务 / 市场 / 技术等）

-三层网关冗余（VRRP）

-二层无环网络（MSTP）

-DHCP 集中分配（DHCP Server + Relay）

-内网访问外网（NAT）

-外网访问内网服务（可拓展：NAT Server）

实验思路

1）先完成最基础的二层网络：

  • 划分 VLAN（10 / 20 / 30 / 50 / 66 等）
  • 接口划分：
    • 接入端口 → access
    • 交换机互联 → trunk

2）因为存在冗余链路，必须控制环路：

  • 启用 MSTP
  • 所有交换机：
    • region-name 一致
    • VLAN → instance 映射一致

3）在汇聚交换机上：

  • 为每个 VLAN 创建 Vlanif 接口
  • 配置 IP 地址

4）在 SW5 / SW6 上：

  • 为每个 VLAN 配置 VRRP

设计原则：VRRP主设备 = MSTP根桥

例如：

  • VLAN10：
    • SW5 → VRRP Master
    • SW5 → MSTP Root

5）DHCP Server

  • 为每个 VLAN 建地址池
  • 配置：
    • network
    • gateway（VRRP地址）
    • excluded 地址

6）路由

实现内网访问外网

  • 汇聚 → NAT：
    • 静态路由指向 NAT
  • NAT → ISP：
    • 默认路由

7）外网访问内网：NAT Server

在 NAT 出口：

公网IP:端口 → 内网IP:端口

例如：

100.1.1.1:2005 → 192.168.10.251:23

实验总结：

问题1：由于是全部关闭重新配置，在配置原先的步骤二的基础的时候发现终端一直有几个获取不了地址，检查了很久也没有问题，后面问gpt，说是软件缓存问题，导致有些地址信息被认为已经分配，出现冲突。

解决1：直接关闭整个软件，在电脑资源管理杀掉软件进程，重新打开配置。

问题2：NATserver正确配置后，client1还是不能访问WEB服务器，后面发现是，NAT和服务器不是直连，需要静态路由。

解决2：在NAT配置ip route-static 192.168.66.0 24 192.168.16.2
